# Система за управление на събития (Event Management System)

Уеб система за организатори на събития — от създаване на събитие и продажба на
билети, до check-in на място чрез QR код и финални отчети за посещаемост.

Индивидуален практически проект по разработка на софтуер.

## Какво прави системата

### Роли

| Роля | Права |
|---|---|
| **Администратор** | Пълен достъп: всички събития, всички отчети, управление на потребителите и ролите им, административен панел |
| **Организатор** | Създава и управлява **собствените** си събития, билетните им типове и програма; извършва check-in; вижда отчетите им |
| **Участник** | Разглежда публикувани събития, регистрира се, плаща (симулирано) и получава билети с QR код |

### Модули

**1. Събития**
- Създаване на събитие с програма, локация и брой места
- Управление на билетни типове и цени (с отделна квота за всеки тип)
- Жизнен цикъл: чернова → публикувано → приключило / отменено

**2. Регистрация**
- Онлайн регистрация и резервация на билет
- Симулация на плащане (банкова карта / банков превод / в брой)
- Генериране на уникален, криптографски подписан QR код за всеки билет
- Преглед на закупените билети с всички данни по покупката и изтегляне на
  QR кода като PNG файл (меню „Моите билети“ горе вдясно)

> Всички суми в системата са в **евро (€)**.

**3. На място (check-in)**
- Сканиране на QR код през камерата на устройството
- Ръчно въвеждане на код като резервен вариант
- Проследяване на реалния брой присъстващи в реално време
- Дневник на всички сканирания, включително отхвърлените

**4. Комуникация и отчети**
- Потвърждения по имейл с прикачени QR кодове
- Автоматични напомняния преди събитието
- Отчет за посещаемост и приходи по събитие, с графики и експорт в CSV

## Инсталация

### 1. Създаване на базата данни

Отворете `psql` като потребител `postgres` и изпълнете:

```sql
CREATE ROLE ems_user WITH LOGIN PASSWORD 'ems_password' CREATEDB;
CREATE DATABASE event_management OWNER ems_user ENCODING 'UTF8' TEMPLATE template0;
GRANT ALL PRIVILEGES ON DATABASE event_management TO ems_user;
```

Правото `CREATEDB` е необходимо, за да може Django да създава временната база
при изпълнение на тестовете.

На Windows `psql` се намира в `C:\Program Files\PostgreSQL\17\bin\psql.exe`:

```bash
"C:\Program Files\PostgreSQL\17\bin\psql.exe" -U postgres -h 127.0.0.1
```

### 2. Виртуална среда и зависимости

```bash
python -m venv .venv
```

Активиране на средата:

```bash
.venv\Scripts\activate
```

(на Linux/macOS: `source .venv/bin/activate`)

```bash
pip install -r requirements.txt
```

### 3. Конфигурационен файл

Копирайте примерния файл и попълнете стойностите:

```bash
copy .env.example .env
```

Задължително сменете `SECRET_KEY` със случаен низ. Той се използва и за
подписване на QR кодовете на билетите, затова не бива да се публикува.

Ако сте използвали други име/парола за базата, поправете `DB_USER` и
`DB_PASSWORD` в `.env`.

### 4. Създаване на таблиците

```bash
python manage.py migrate
```

### 5. Зареждане на демонстрационни данни (по избор)

```bash
python manage.py seed_demo
```

Създава потребители и в трите роли, локации, 6 събития в различни състояния,
билетни типове, програма, регистрации, плащания и извършени check-in-и.

За повторно зареждане „на чисто“:

```bash
python manage.py seed_demo --reset
```

Ако не използвате демонстрационните данни, създайте си администратор ръчно:

```bash
python manage.py createsuperuser
```

## Стартиране

```bash
python manage.py runserver
```

Системата е достъпна на <http://127.0.0.1:8000/>, а административният панел —
на <http://127.0.0.1:8000/admin/>.

В режим на разработка (`DEBUG=True`) писмата **не се изпращат реално**, а се
извеждат в конзолата на сървъра. Така целият поток може да се демонстрира без
пощенски сървър. За реално изпращане задайте `DEBUG=False` и попълнете SMTP
настройките в `.env`.

## Проверка при натоварване

Скриптът `scripts/load_test.py` симулира много участници, които се борят за
едни и същи места, и проверява дали системата продава повече билети от
наличните.

Стартирайте сървъра в отделен прозорец:

```bash
python manage.py runserver
```

След това пуснете проверката:

```bash
python scripts/load_test.py --users 60 --capacity 20
```

Скриптът сам създава събитието и участниците и ги изтрива накрая (освен ако не
подадете `--keep`).

**Измерен резултат** (60 едновременни заявки за 20 места, вграден сървър на
Django на локална машина): 20 успешни резервации, 40 отказани, **0 свръхпродажба**.

> Вграденият сървър `runserver` не е предназначен за натоварване и при много
> едновременни връзки част от тях може да получат грешка при свързване. Това е
> ограничение на сървъра за разработка, а не на самата система — важното за
> проверката е, че броят продадени билети никога не надхвърля капацитета.

## Изпращане на напомняния

Напомнянията се изпращат от отделна команда, която се пуска периодично:

```bash
python manage.py send_reminders
```

Полезни опции:

```bash
python manage.py send_reminders --hours 48 --dry-run
```

- `--hours N` — събития, започващи в следващите N часа (по подразбиране 24)
- `--dry-run` — само показва кой би получил писмо, без да изпраща
- `--event <slug>` — само за едно конкретно събитие

Командата пропуска участниците, на които вече е изпратено напомняне, така че
многократното ѝ изпълнение е безопасно.

### Периодично изпълнение

**Windows (Task Scheduler):** създайте задача, която всеки ден изпълнява

```
D:\път\до\проекта\.venv\Scripts\python.exe D:\път\до\проекта\manage.py send_reminders
```

**Linux (cron):** ежедневно в 9:00 ч.

```
0 9 * * * /път/до/проекта/.venv/bin/python /път/до/проекта/manage.py send_reminders
```

## Ключови технически решения

### Защита от свръхпродажба при едновременни регистрации

Наивната проверка „има ли свободно място → създай билет“ се проваля, когато две
заявки пристигнат едновременно: и двете виждат едно свободно място и продават
едно и също място два пъти.

Решението в `registration/services.py` е песимистично заключване:

1. цялата резервация е в една транзакция;
2. редът на събитието се заключва със `SELECT ... FOR UPDATE`, така че втората
   заявка изчаква;
3. свободните места и квотите се преброяват **отново**, вече вътре в
   заключението, върху актуалните данни.

Резервацията е „всичко или нищо“ — при недостиг не се създават частични билети.

### Сигурност на билетите

Защитата е на две нива:

**Срещу фалшифициране.** QR кодът не съдържа гол идентификатор, а стойност,
подписана с тайния ключ на приложението (HMAC-SHA256 чрез `django.core.signing`).
Промяна дори на един знак прави подписа невалиден и билетът се отхвърля още
преди справка в базата данни.

**Срещу повторно използване.** Връзката между `CheckIn` и `Ticket` е „едно към
едно“. Базата данни физически не позволява втори запис за същия билет — дори
две сканирания да се случат в един и същи момент от различни устройства, второто
получава грешка за нарушена уникалност и се отчита като опит за дублиране.

Всяко сканиране, успешно или не, се записва в дневника `ScanLog` — това е
одитната следа на системата.

### Точност на отчетите

Всички числа се получават с агрегиращи заявки към базата (`SUM`, `COUNT`), а не
чрез обхождане на записите в Python. Паричните суми се пазят в тип `NUMERIC`
(`DecimalField`), а не в число с плаваща запетая, което би натрупало грешка при
закръгляване.

Цената на билета се записва в момента на покупката — по-късна промяна на цената
на билетния тип не променя вече издадени билети и не разваля старите отчети.

### Проследяване в реално време

Страницата за check-in анкетира адрес `/checkin/<събитие>/stats/` на всеки 5
секунди и обновява брояча на присъстващите. Съзнателно не са използвани
WebSockets — те биха наложили ASGI сървър и допълнителна инфраструктура без
реална полза при този обем данни.

### Адреси на кирилица

Стандартният `slugify` на Django изхвърля кирилските букви и заглавие като
„Концерт „Класика под звездите“ би дало празен адрес. Затова в `events/utils.py`
текстът първо се транслитерира на латиница по официалната българска
транслитерация, а след това се подава на `slugify`:

„Концерт „Класика под звездите“ → `kontsert-klasika-pod-zvezdite`
